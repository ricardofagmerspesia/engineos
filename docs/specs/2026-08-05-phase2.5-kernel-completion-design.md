# Phase 2.5 — kernel completion & operational hardening — design

Date: 2026-08-05
Status: approved-in-brainstorm, pending plan
Risk: medium (kernel public surface grows; runner behavior changes; no production systems)
Parent: Phase 2 vertical MVP (engineer-spec-ia-pattern#7), T1–T9 all closed
Repos touched: `engineos` (kernel), `ai-se-os` (runner)

## Problem

T9's live run proved the pipeline works end to end, and in doing so exposed
four gaps:

1. **The runner still holds private agent definitions.** Only `product-spec`
   is read from the kernel; `implement` and `document` run on hardcoded
   placeholder prompts in `bin/ai-se-os.js` that imitate kernel agents without
   reading them — exactly the drift the kernel-as-single-inventory principle
   (T8) exists to prevent. Worse, the `document` placeholder imitates an agent
   that does not exist: the kernel has no docs agent at all.
2. **`security-review` is theatre.** When the state triggers (security-
   sensitive path touched), it falls through to the fake scripted executor and
   returns OK having reviewed nothing. The kernel's `security-reviewer` agent
   exists and is never dispatched.
3. **Runs are unpriceable and uncounted.** The journal records tokens per
   state but nothing converts them to cost; T9's run burned tokens nobody can
   price.
4. **The shared checkout is a contamination vector.** PR #4 shipped incomplete
   because `implement` ran against a checkout left dirty by a previous buggy
   run and concluded the feature already existed. Worktree isolation was
   documented as "the caller's responsibility" and the caller (us) didn't do it.

Additionally, the spec-approval gate (user story 17, Phase 2 spec) exists but
auto-approves — it has never once asked a human anything.

## Decision — five units

Topology decision first: the agent graph **stays one agent per workflow
state**. The SDK-native leader-with-roster and deterministic runner-fan-out
options were considered and deferred — both are Phase 4's domain-manager
territory, and both depend on this phase's kernel completion anyway. Rejected
for now, not forever.

### U1 — kernel: docs-writer agent (engineos)

New `agents/docs-writer.md`: build tier (`model: sonnet`), tools
Read/Grep/Glob/Edit/Write, canonical Return-format envelope, alias per kernel
convention. Passes every existing integrity check (`validate-engineos.sh`,
drift guards, gen scripts re-run). This is a T8-style contribution — the
kernel gains the agent BEFORE the runner points at it.

### U2 — kernel: capability bindings (engineos)

`registries/capabilities.json`:
- `document` → `docs-writer` (the "no dedicated kernel agent yet" note goes away).
- New capability `security-review` → `security-reviewer`, risk_floor high.
- `implement` → `backend-coordinator` and `validate` → `test-writer` are
  already bound; unchanged.

`registries/agents.json` + `commands/agents/*` regenerated. MINOR version bump.

### U3 — runner: all agents from the kernel + real security-review (ai-se-os)

- Delete the three placeholder definitions in `bin/ai-se-os.js`.
  `implement`, `document` (and `validate`, for the no-shell-flag path) load
  via `loadKernelAgent()` — same path `product-spec` already uses: capability
  binding checked first, `## Return format` stripped, literal
  `WORKING_DIRECTORY` grounding appended.
- `loadKernelAgent()` gains a tool filter: kernel `tools` lists include
  entries meaningless in headless SDK dispatch (`Skill`, `mcp__nestjs`).
  Filter to the SDK-available allowlist (Read, Grep, Glob, Bash, Edit,
  Write), warn on stderr about anything dropped. An agent whose tools filter
  to empty is a loud boot failure.
- `security-review` enters `stateAgents` → dispatches the kernel's real
  `security-reviewer`. Status mapping: the kernel envelope's `CRITICAL` has
  no runner equivalent — map to `FAILED` with the reason preserved verbatim,
  so blocking findings fail the run at `security-review` (report in the run
  log as evidence; no PR opens).

### U4 — runner: cost ledger (ai-se-os)

**Amended during implementation — see "Deviations" below.** As built:

- No price table. The Claude Agent SDK reports real cost per dispatch
  (`total_cost_usd`), carried straight through — the provider's own
  arithmetic, which survives model rebinds and cache pricing that a
  hand-maintained table cannot model.
- Journal record and run report gain `cost_usd` per state and total per run,
  accumulated across every attempt the retry ladder made (a state that burned
  three dispatches reports all three), and recorded on FAILED and BLOCKED
  transitions too — those are the runs that cost the most.
- Reported as `null`, never `0`, when nothing reported a cost. A run of fakes
  costing nothing and a real run whose cost went unreported are different
  facts.

### U5 — runner: automatic worktree isolation + human spec-approval (ai-se-os)

Worktree:
- When `AI_SE_OS_AGENT_SDK=1`: runner runs `git worktree add` from the HEAD
  of `AI_SE_OS_AGENT_CWD` into a temp directory, points every agent (and the
  shell validator) at the worktree.
- Success → worktree removed. Failure → kept, path printed, for debugging.
- `AI_SE_OS_AGENT_CWD` not a git repo → loud error, no silent fallback.
- `AI_SE_OS_NO_WORKTREE=1` opts out (current behavior).
- The original checkout is never again touched by an agent.

Spec-approval:
- Armed only in live mode (`AI_SE_OS_AGENT_SDK=1`) with `specApprovalEnabled`.
- stdin is a TTY: print the spec file `author-spec` wrote, ask
  `approve? [y/N]`. `y` → continue; anything else → run fails at
  `spec-approval`, resumable (`--resume` re-asks).
- stdin not a TTY (CI): fail with an explanatory message. Live mode never
  auto-approves silently.
- The fake/test path keeps the current injectable auto-approve default —
  every existing test unchanged.

## Dependencies and order

U1 → U2 (binding needs the agent) → U3 (runner needs the binding).
U4 and U5 are independent of each other and of U1–U3; they only share
`bin/ai-se-os.js` and runner internals with U3, so they serialize with U3 on
files, not on meaning.

## Out of scope

- Leader-agent-with-roster and runner fan-out (Phase 4 — domain managers).
- Durable workflow engine, tracing (rest of Phase 3).
- Pricing API integration; the table is static by design.
- Baseline comparison against manual delivery — still an open gap, noted in
  the runner README; not this phase's job.
- The engineos-global-hooks-leak into agent-driven repos (observed in T9:
  `.engineos/` scaffold appeared in the scratch repo uninvited). Real issue,
  belongs to engineos hook gating, tracked separately.

## Testing

- Kernel units (U1/U2): existing integrity suite + drift guards; planted-
  breakage cases already cover unknown agents/tiers.
- Runner units: same two-tier discipline as all of Phase 2 — deterministic
  tests with fakes for every new behavior (tool filtering, CRITICAL→FAILED
  mapping, cost arithmetic, worktree lifecycle via injectable exec, TTY/non-
  TTY approval via injectable stdin), live tier stays opt-in and unexercised
  without credentials.
- Every unit ends with the full suite green, build clean, and the standard
  two-axis review (Standards + Spec) before its commit closes.

## Acceptance criteria

- [ ] `bin/ai-se-os.js` contains zero agent prompt literals; every dispatched
      agent definition originates in `<kernel>/agents/*.md`.
- [ ] A live-mode run touching a security-sensitive path dispatches the real
      `security-reviewer`; a CRITICAL report fails the run before any PR.
- [ ] Journal and report show `cost_usd` per state and per run, including on
      FAILED/BLOCKED states and across `--resume`; states whose executor
      reported no cost read `null`, not 0.
- [ ] Two consecutive live runs against the same target repo cannot
      contaminate each other (worktree per run, fresh from HEAD).
- [ ] With spec approval enabled in live mode, the run halts until a human
      answers; `N` leaves a resumable failure at `spec-approval`.
- [ ] Kernel version bumped MINOR; all integrity checks green in both repos.

## Deviations from this spec, and why

Recorded here rather than left to commit archaeology.

1. **U3 said to strip the `## Return format` section** from dispatched prompts
   (carried over from a T9 fix that removed an engineos-only path reference).
   Doing so would have defeated this phase's own security criterion: the runner
   must PARSE that envelope to see a CRITICAL verdict, and an agent never told
   to emit it never emits one. The section stays; only the kernel-internal
   references inside it are rewritten. The spec contradicted itself and the
   implementation resolved it.

2. **U4's static price table was dropped** for the SDK's own
   `total_cost_usd`, and unreported cost reads `null` rather than `0`. Both are
   improvements over what this document originally specified, and U4 above has
   been amended to match what shipped.

3. **CRITICAL maps to BLOCKED, not FAILED.** U3 said FAILED. FAILED enters the
   retry ladder, so a blocking security finding would be re-dispatched twice
   more with a model escalation — which `rules/parallelism.md` forbids outright
   ("never retry these... security risk") and which buys a more confident wrong
   answer at 3x the cost of the roster's most expensive agent. BLOCKED is the
   status the runner never retries. Its usual sense is "missing input", which
   this is not, so the reason and evidence carry the agent's own CRITICAL
   report.
